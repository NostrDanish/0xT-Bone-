## Top recommendations (ranked, with effort S/M/L)

1. **[M] Upgrade the ZIP-upstream sync from "manual diff" to a vendor-branch 3-way process.** `FORK.md` documents download→unzip→diff→cherry-pick. That loses track of what you already rejected and makes every sync a from-scratch diff. Proposed process:
   - Keep a branch `vendor/upstream` that contains *only* the verbatim extracted ZIP contents, one commit per upstream drop, tagged `upstream-v0.3.36` etc. (commit message = ZIP filename + its SHA-256).
   - Sync = `git merge vendor/upstream` into `main` (or a `sync/` branch): git's 3-way merge replays only *new* upstream changes and surfaces your fork edits (`applicationId`, alarm action, packaging excludes, signing block) as conflicts instead of silent overwrites.
   - Record the ZIP's sha256 + the release page URL in `vendor/UPSTREAM.md` so the provenance of each drop is auditable (a ZIP from a release page has no signatures — the hash log is your only supply-chain record).
   - Keep `scripts/privacy-check.sh` running on every sync merge, as you already do on PRs.
2. **[S] Make the debug-key release fallback fail-closed for *tagged* releases.** `app/build.gradle.kts` currently falls back to the debug keystore with only a `logger.warn`. That is fine for local/CI smoke builds but dangerous for `v*` tags: a debug-signed APK has a publicly known key — anyone can publish "updates" that Android will accept as same-signature upgrades for users who installed a debug-signed build.
   Fix: gate the fallback behind an explicit opt-in, e.g. `ALLOW_DEBUG_SIGNED_RELEASE=1` env var; in `build-release.yml` (tag pushes) do NOT set it, so a missing keystore secret fails the build loudly instead of shipping a debug-signed APK. Keep the fallback for local dev with the flag. Cheaper variant: in the workflow, after build, assert the APK's signing cert is not the well-known Android debug cert (`apksigner verify --print-certs` + grep against the known debug SHA-256) and fail the job if it matches (S).
3. **[S] Dependency refresh pass on the version catalog.** `gradle/libs.versions.toml`: AGP `8.3.2`, Kotlin `2.0.0` (+ksp `2.0.0-1.0.21`), Hilt `2.51.1`, composeBom `2024.09.01`, media3 `1.4.1`, okhttp `4.12.0`, bcprov `1.78.1`, coil `2.6.0`. All 1–2 years behind; Kotlin is on the 2.2.x line and AGP on 8.13.x. Bump Kotlin+KSP+AGP together (they move in lockstep), then composeBom/media3 (M for the combined pass; do Kotlin/AGP first, UI libs second).
4. **[S] `targetSdk = 34`** — Play requires 35+ for new uploads since Aug 2025; even for zapstore-only distribution, 35 buys you the edge-to-edge and predictive-back defaults on purpose rather than by accident (S).

## Quick wins (code/config)

- `versionCode = 64` hardcoded in `app/build.gradle.kts` while `make-release.sh` manages versions — the 0xVector-style version.properties consistency check would prevent a stale-code release (S).
- `excludes += "META-INF/services/**"` — this strips *all* ServiceLoader metadata; BC's is the known offender but blanket exclusion can silently break libraries that need it. Narrow to the specific BouncyCastle entries if any runtime issue appears (S).
- Duplicate app label ("T-bone" for both installs) — consider `T-boneⒻ`/icon badge; documented already, just decide (S).
- `index.html` + `package.json` + `vite.config.ts` + `src/` at repo root alongside the Android app — a second stack (landing page?). If it's just the website, move under `web/` to keep the Android root clean and make the two build systems obvious to CI (S).
